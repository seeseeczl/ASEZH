# 对抗性审计报告 — ASEZH 0.0.14 / 0.0.15 汉化覆盖补齐

## 审计边界

- 审计对象：`53f006a`（v0.0.13）之后的全部未提交改动，覆盖 0.0.14（界面文案钩子 + 审计工具）与 0.0.15（节点标题覆盖）。
- 重点：新增的 14 条界面/标题锚点、词典增量（1433 → 1447）、原生白名单增量（290 → 298）、审计命令本身、合成 fixture 与门禁脚本。
- 方法：通读全部 diff；对每条新锚点在许可 ASE 1.9.9.5 上做空白容错匹配校验；跑合成与许可 ASE 全生命周期、EditMode、静态与 OpenSpec 校验；对审计命令做正反例复核。
- 非目标：不覆盖 Windows / 其他 Unity 版本；不做真实画布逐节点截图比对。
- 未覆盖范围：0.0.14/0.0.15 的锚点未在 ASE 1.9.8.x 上验证（该版本已不在必选门禁内，见 AA-GOV-001）。

## 威胁与失败模型

- 资产：消费者工程里的 ASE 源码、节点标题显示正确性、包的可回滚性。
- 攻击者能力：不同 ASE 版本的源码差异、Unity 对 asmdef/meta 的重写、用户重命名节点、旧版 ASEZH 留下的中间状态。
- 最贵失败：锚点错配导致整次预检被拒（无法接入），或把用户数据/标识符写坏。
- 本次新增的信任边界没有变化：仍只改显示参数，未声明的差异一律 fail-closed。

## Findings

### AA-CORR-003 — 审计命令的失败条件漏掉节点三类缺口（P3，本次审计发现并在提交前修复）

- 位置：`scripts/audit_localization.py` → `main()`
- 触发条件：`--fail-on-missing` 运行在存在节点标题缺口的 ASE 版本上。
- 错误行为：命令会打印 `node_types_not_allowlisted` / `node_titles_missing` / `categories_missing`，但退出码仍为 0，只有 `hooked_missing` 与 `wrapper_missing` 计入失败。
- 影响：正好漏掉用户本次反馈的"节点名没汉化"这一类；把它放进 CI 也拦不住回归。
- 证据等级：已验证（代码路径 + 修复前后退出码）。
- 状态：已修复。五类缺口现在都计入 `--fail-on-missing`；对许可 ASE 1.9.9.5 复跑为 `exit=0` 且五项计数为 0。

### AA-DOC-002 — `unhooked` 清单会高估缺口（P3，本次审计发现并在提交前修复）

- 位置：`scripts/audit_localization.py` → 模块说明与 `unhooked` 分支
- 触发条件：把文案先存进字段、再在调用处翻译的间接绘制路径（例如 `TriplanarNode.cs` 里用于重命名的文本框）。
- 错误行为：这些位置被计入 `unhooked`，读起来像"完全没钩子"。
- 影响：后续按清单补钩子会浪费工时，甚至给本不该翻译的重命名输入框加钩子。
- 证据等级：已验证（本轮 170 条候选中含该文件与 `MenuParent` 等定义点）。
- 状态：已修复说明（模块说明与 CLI 帮助注明这是需要人工判断的候选清单）。计数仍保留原始语义，不假装精确。

### AA-RISK-001 — 新增 14 条锚点扩大"整次预检被拒"的暴露面（P2，未修复）

- 位置：`Editor/Installer/ASEUiCaptionPatchCatalog.cs`（13 条）与 `ASENativePatchCatalog.cs`（ToggleSwitch 标题）
- 触发条件：消费者使用 1.9.8.x、裁剪版或改动过这些行的 ASE 源码。
- 错误行为：任一新锚点不匹配 → `HasInvalidResults` 判定 `mismatch` → 整次 Apply 被拒绝，连本来能接的其它钩子也无法接入。
- 影响：纯粹为了多翻译几句界面文案，却可能让整个汉化无法安装。锚点已全部在 1.9.9.5 上校验，但该版本之外的组合没有证据。
- 证据等级：高置信推断（代码级推理；1.9.8.x 未运行）。本次许可门禁全绿只证明 1.9.9.5 可用。
- 状态：未修复，交 `AA-OPT-007`。这是把"覆盖率"优先于"兼容性"的已知代价，需要维护者决策。

### AA-GOV-001 — 必选门禁只覆盖单一的 ASE 1.9.9.5（P2，未修复，沿用上次审计）

- 位置：`scripts/validate_delivery.py`、`openspec/specs/release-regression-gates/spec.md`
- 触发条件：任何锚点或白名单改动。
- 错误行为：1.9.8.x 不再被任何自动检查覆盖，而仓库仍保留面向它的锚点与历史证据。
- 影响：与 AA-RISK-001 叠加，使得"扩覆盖"与"保兼容"两个目标都无法被现有门禁验证。
- 证据等级：已验证（本次门禁仅声明 1.9.9.5）。
- 状态：未修复，`AA-OPT-002`。

### AA-TEST-003 — 节点覆盖只能靠许可源码人工核对（P3，未修复）

- 位置：`scripts/audit_localization.py`、`Tests/Fixtures/FakeASE/`
- 触发条件：有人删掉白名单条目或词条后提交。
- 错误行为：合成 fixture 不含真实节点声明，公开检查不会发现节点覆盖回退；只有维护者手动跑审计命令才会暴露。
- 影响：回归保护依赖人记得跑命令，缺少自动闸门。
- 证据等级：已验证（合成 fixture 中没有任何 `[NodeAttributes]`）。
- 状态：未修复，`AA-OPT-008`。

## 已检查未发现可行动缺陷的区域

- 锚点正确性：14 条新锚点逐条在许可 ASE 1.9.9.5 上做空白容错匹配，全部命中；应用后 `VerifyApplied` 为 `applied`，说明 Marker 判定与 ReplaceAll 语义正确。
- 既有行为未被改写：`ScreenColorNode` / `StaticSwitch` 的标题锚点在重构后生成的 Find/Replace 与重构前逐字一致。
- 白名单安全边界：仍按类型全名精确匹配，未放宽成前缀/基类匹配；`Flyme` 分类否决与"仅在标题等于默认名时翻译"两条保护未动。白名单 298 条无重复。
- 词典安全：16 + 14 条新增词条无 (table, key) 重复；`Position` 等通用词只进 `node_title`，端口查询走独立的 `port_label` 表，不会被误用。
- 合成 fixture：新增 6 个 fixture 文件均包在 `#if false` 中，不会参与编译；`MANAGED_NAMES` 已同步，preimage 校验覆盖到新文件。
- 交付一致性：package.json / README / CHANGELOG 三处版本一致（0.0.15），CHANGELOG 连续 `0.0.15 → 0.0.14 → 0.0.13`；OpenSpec 严格校验通过；`Editor` 无超 400 行文件。
- 幂等性：对已汉化的 ASE 树扫描 + 接入不会改写文件（上次审计的实测结论在本批次未回退）。

## 结论摘要

- 问题统计：P0=0，P1=0，P2=2，P3=3；其中 2 条 P3 已在提交前修复并复验。
- 总体判断：本批次的功能改动（节点白名单、词条、标题钩子）在目标环境验证完整，未发现发布阻断项；剩余 P2 是"扩覆盖 vs 保兼容"的结构性取舍，不影响本次 0.0.15 在 ASE 1.9.9.5 上的可用性。
- 发布建议：**可合并**。建议维护者在下一批次处理 `AA-OPT-007`（可选锚点）与 `AA-OPT-002`（第二 fixture），再继续扩大汉化范围。
