# 对抗性审计报告 — ASEZH 0.0.13 锚点兼容变更

## 审计边界

- 审计对象：工作区相对 `b8aea35` 的全部未提交改动（`Editor/`、`Editor/Tests/`、`scripts/`、`docs/`、`openspec/`、`package.json`），重点是新增的锚点变体机制与 asmdef 引用改写。
- 项目根目录：`/Users/long/GitHub/ASEZH`
- 写入授权：允许落盘本报告与优化计划；业务代码修改经用户「没问题就推送并发布新版本」授权，仅限发布阻断项。
- 审计方法：静态通读全部 diff + 调用方/失败路径追踪 + 定向运行真实门禁、EditMode 测试与"用户既有接入树"非破坏性验证。
- 非目标：不评估 ASE 自身实现；不覆盖 Windows/其它 Unity 版本；不做 UI 视觉验收。
- 未覆盖范围：asmdef 其它引用的 fail-closed 分支只做了静态可达性判断，未构造运行用例（见 AA-CORR-001）。

## 威胁与失败模型

- 资产：消费者工程里的 ASE 源码（唯一不可重建资产）、Shader 生成语义、包的可回滚性。
- 攻击者能力：不受信任的 ASE 版本差异、Unity 自身对 `.asmdef`/`.meta` 的重写、用户手工编辑、旧版 ASEZH 留下的中间状态。
- 最贵失败：把用户的 ASE 源码改坏或改错且不可恢复；或撤回报告成功而实际留下引用，导致卸载 ASEZH 后 ASE 编译失败。
- 本次变更的信任边界未变：安装器仍只写"已声明锚点命中"的片段，未声明漂移一律 fail-closed。

## Findings

### AA-CORR-001 — asmdef 撤回丢失 fail-closed 保护（P2，本次审计发现并在提交前修复）

- 位置：`Editor/Installer/ASEZHPatchTransforms.cs` → `ReverseAseAssemblyReference`
- 触发条件：`AmplifyShaderEditor.asmdef` 的 `references` 数组内**没有** `ASEZH.Editor`，但文件其它位置（例如 `precompiledReferences`）含字符串 `"ASEZH.Editor"`。
- 错误行为（修复前）：改写结果与原文件相同，仍返回 `removed`。改动前的实现用 `next == text` 判定该情况并返回 `mismatch`；本次重写把它删掉了。
- 影响：撤回报告成功但 ASE 程序集仍引用 `ASEZH.Editor`。用户随后卸载 ASEZH 时，ASE 会因找不到程序集而编译失败，且失败点远离撤回动作。
- 证据等级：高置信推断。静态代码分析确定该分支可达且返回状态确定；未构造含 `precompiledReferences` 的 fixture 运行用例。
- 状态：已修复。`ReverseAseAssemblyReference` 恢复"改写未生效即 `mismatch`"判断；修复后 `--release` 门禁仍为 `pass`（`/private/tmp/asezh-release-gate-0.0.13/delivery-manifest.json`）。补测任务见 `AA-OPT-001`。

### AA-CORR-002 — 备用锚点接入后仍被判定为"未接入"（P2，本次审计发现并在提交前修复）

- 位置：`Editor/Installer/ASEZHPatchAnchors.cs` → `IsRemoved`
- 触发条件：`native-language-layout` 用 1.9.9 签名锚点接入后，再对同一文件执行撤回路径（无回执分支）。
- 错误行为（修复前）：守卫块插在方法开括号之后，因此"锚点原文"在接入后仍然存在；`IsRemoved` 只查锚点在否，于是把已接入文件判成"源码已是接入前片段"。
- 影响：撤回路径对 1.9.9 接入的文件会静默走"已撤回"捷径，不做真正还原；同时使新增用例失败。
- 证据等级：已验证。EditMode 用例 `NativeLayoutAnchor_MatchesLegacyAndCachedOnNodeLayoutSignatures` 直接失败（`Expected: False But was: True`），修复后 23/23 通过（`/private/tmp/asezh-editmode-results4.xml`）。
- 状态：已修复。`IsRemoved` 改为先判断"任一变体的替换文本是否仍在"，再判断锚点原文。

### AA-GOV-001 — 必选门禁从单一 1.9.81 切到单一 1.9.9.5，旧版覆盖归零（P2，未修复）

### AA-OPS-001 — 无回执的既有接入树在 Remove 后不可恢复，且无提示（P2，未修复）

- 位置：`Editor/Installer/ASEZHPatchTransaction.cs`（`plans.Count == 0` 直接 NoOp 返回，不写回执）、`Editor/Installer/ASEZHPatchTransforms.cs` → `Reverse`
- 触发条件：ASE 树已被接入（由旧版 ASEZH 或手工产生），当前安装目录下没有对应回执；用户先 Apply 再 Remove。
- 错误行为：Apply 因"所有受管文件已处于目标状态"进入 `NoOp` 并**不保存回执**；随后 Remove 只能靠反向变换，把文件还原成官方 ASE 片段并报 `removed`。
- 影响：用户原有的接入状态无法恢复（回不到"接入前内容"），若同一行存在用户手工改动会被一并覆盖；整个过程没有提示。
- 证据等级：已验证。用维护者既有接入的 ASE 1.9.9.5 树复现：门禁 preimage 校验 `apply_remove_preimage_restored=fail`，`before` 为已汉化哈希、`after` 为官方原文哈希；同一棵树在无接入状态下则恢复校验 `pass`。
- 状态：未修复。属设计边界（无 preimage 无法还原），但缺少提示与文档，交由 `AA-OPT-003`。

## 已检查未发现可行动缺陷的区域

- 锚点变体对既有补丁的影响：`Variants` 中 v1（`LegacyReplace`）与 v0 共用同一 Replace，新增接受面只来自 v2（`AltFind/AltReplace`），即只影响 `native-language-layout`；未发现对其它 21 条补丁的判定漂移。
- 幂等性：接入后"锚点原文仍在"的形态由替换文本判定为 `applied`；真实门禁 `VerifyApplied` 与 EditMode 用例均通过。
- 空 `Find` 新语义：目录中不存在空 `Find` 的补丁，新 `TryMatch` 的放宽不可达。
- 正则安全：`s_aseReferences` 为定值模式、字符类线性匹配，无回溯放大；匹配对象是消费者 asmdef，不接受远程输入。
- 非破坏性：对维护者"已汉化"的 ASE 树执行 Baseline/Apply/VerifyApplied，用户工程 0 个文件发生变化（本次审计脚本实测 `用户工程文件被改动: False`）。
- 版本与交付：`package.json`/`README`/`CHANGELOG` 三处版本一致（0.0.13）；OpenSpec 严格校验 8/8；静态检查 12/12；`Editor` 无超 400 行文件；meta GUID 无重复。
